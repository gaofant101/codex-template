## 4. 产品阶段

### 阶段一：想法澄清

目标：把模糊想法变成清晰的问题、用户、场景和价值假设。

输入材料：

- 初始想法：
- 目标用户：
- 现有痛点：
- 竞品或参考：
- 业务约束：

需要产出：

- 产品一句话定位
- 用户画像
- 核心问题清单
- 关键使用场景
- 初步价值假设
- 当前阶段不做的内容

验收标准：

- 能清楚回答“给谁用、解决什么、为什么现在做”
- 能区分核心需求和边缘需求
- 能列出至少 3 个真实使用场景

### 阶段二：需求定义

目标：把产品想法拆成可执行的功能需求。

输入材料：

- 阶段一结论
- 用户流程
- 业务规则
- 权限规则
- 数据来源
- 异常场景

需要产出：

- 功能清单
- 用户故事
- 业务流程
- 页面清单
- 权限矩阵
- 字段清单
- 异常状态
- MVP 范围

需求格式：

```text
需求名称：
目标用户：
使用场景：
前置条件：
操作流程：
正常结果：
异常结果：
权限要求：
数据字段：
验收标准：
优先级：
```

优先级规则：

- P0：没有它产品无法成立
- P1：影响核心体验，但可以后补
- P2：提升效率或体验
- P3：锦上添花

验收标准：

- 每个核心功能都有明确用户、流程和结果
- MVP 范围清楚
- 异常情况被列出
- 没有只写“支持某功能”但没有说明行为的需求

### 阶段三：产品设计

目标：把需求转成用户可以理解和操作的产品界面。

输入材料：

- 功能清单
- 页面清单
- 用户流程
- 字段清单
- 权限矩阵
- 品牌或设计规范

需要产出：

- 信息架构
- 页面结构
- 关键操作路径
- 表单设计
- 列表设计
- 详情页设计
- 空状态
- 加载状态
- 错误状态
- 成功状态
- 文案规范

页面设计要求：

```text
页面名称：
页面目标：
访问角色：
入口：
核心信息：
主要操作：
次要操作：
筛选/搜索：
表格/字段：
状态展示：
异常提示：
跳转关系：
```

交互要求：

- 高频操作路径要短
- 危险操作必须二次确认
- 表单必须有校验反馈
- 空状态要告诉用户下一步做什么
- 错误提示要说明原因和解决方式
- 不用营销式表达，优先清晰、准确、可操作

验收标准：

- 用户能从首页完成核心任务
- 每个页面都有明确目的
- 主要操作不被隐藏
- 异常、空状态、加载状态完整
- 页面之间跳转关系清楚

### 阶段四：技术方案

目标：把产品需求转成可开发、可维护、可扩展的技术方案。

输入材料：

- 产品需求
- 页面设计
- 数据字段
- 业务流程
- 权限规则
- 现有技术栈
- 第三方接口

需要产出：

- 技术架构
- 前端模块划分
- 后端模块划分
- 数据模型
- API 清单
- 权限设计
- 状态流转
- 错误码设计
- 日志与监控
- 安全要求
- 部署方案

技术方案格式：

```text
模块名称：
职责：
输入：
输出：
依赖：
核心流程：
数据结构：
接口：
异常处理：
安全要求：
测试重点：
```

API 设计要求：

```text
接口名称：
方法：
路径：
用途：
请求参数：
响应数据：
权限要求：
错误码：
幂等要求：
日志要求：
```

验收标准：

- 关键业务流程能被技术方案完整覆盖
- 数据模型能支撑页面和业务规则
- API 边界清楚
- 权限和异常处理明确
- 没有明显的重复设计或不可维护结构

### 阶段五：开发实现

目标：按照技术方案完成可运行的产品功能。

输入材料：

- 产品需求
- 设计方案
- 技术方案
- API 文档
- 数据模型
- 项目代码

开发要求：

- 遵循现有项目结构和代码风格
- 优先复用已有组件、工具函数和接口模式
- 不做无关重构
- 不引入不必要的新依赖
- 核心逻辑要有必要测试
- 用户可见文案要清晰一致
- 错误处理不能只打印日志

前端要求：

- 页面布局稳定
- 表单校验完整
- 列表支持必要的加载、空状态、错误状态
- 操作按钮有明确反馈
- 移动端或窄屏按项目要求适配
- 不让文字溢出、遮挡或重叠

后端要求：

- 参数校验完整
- 权限校验明确
- 数据变更有事务保护
- 关键操作有日志
- 外部接口失败要有降级或明确错误
- 避免重复提交或重复处理

验收标准：

- 功能可运行
- 核心流程可完整走通
- 异常情况有反馈
- 权限控制符合要求
- 测试通过
- 没有引入明显回归

### 阶段六：测试验收

目标：确认产品功能、体验、数据和异常处理符合预期。

输入材料：

- 需求文档
- 设计方案
- 测试账号
- 测试数据
- 测试环境
- 验收标准

需要产出：

- 测试用例
- 验收清单
- 问题清单
- 修复建议
- 回归测试结果

测试范围：

- 核心流程
- 权限边界
- 表单校验
- 数据准确性
- 异常状态
- 空状态
- 加载状态
- 并发或重复提交
- 兼容性
- 性能风险
- 安全风险

测试用例格式：

```text
用例名称：
前置条件：
操作步骤：
预期结果：
实际结果：
是否通过：
问题说明：
优先级：
```

验收标准：

- P0 问题全部修复
- P1 问题有明确处理结论
- 核心流程无阻断
- 权限和数据正确
- 上线风险可接受

### 阶段七：上线发布

目标：把产品安全、可控地交付给真实用户。

输入材料：

- 已验收版本
- 发布说明
- 数据迁移方案
- 回滚方案
- 监控方案
- 用户通知

需要产出：

- 发布清单
- 发布步骤
- 回滚方案
- 监控指标
- 用户说明
- 运营支持材料

发布清单：

```text
版本号：
发布时间：
发布范围：
影响用户：
新增功能：
变更功能：
修复问题：
数据库变更：
配置变更：
第三方依赖：
回滚方式：
负责人：
```

验收标准：

- 发布步骤清楚
- 回滚方案可执行
- 关键指标可监控
- 用户影响已评估
- 相关人员知道如何处理问题

### 阶段八：上线后迭代

目标：根据真实数据和反馈持续优化产品。

输入材料：

- 用户反馈
- 使用数据
- 错误日志
- 业务指标
- 客服问题
- 运营反馈

需要产出：

- 数据分析
- 问题归因
- 优化建议
- 下一版需求池
- 优先级排序

关注指标：

- 活跃用户数
- 核心流程完成率
- 转化率
- 错误率
- 平均处理时间
- 退款率/失败率/投诉率
- 留存率
- 用户满意度

验收标准：

- 能判断产品是否达成目标
- 能识别主要问题
- 能形成下一轮明确迭代计划
- 不凭主观感觉做优先级
